## 一、系统架构（第 6 页）

### Q1：为什么前端用 Next.js、后端单独用 NestJS，而不是全栈 Route Handlers？

**答：** 课程要求后端框架必须是 **NestJS**。我们把 **Next.js 限定为 UI 层（3000）**，**NestJS 作为唯一业务 API 供应方（3001，`/api` 前缀）**。这样 API 可被前端、脚本客户端（`anitrack-tester`）和 Swagger **独立调用**，符合 **API-first**；业务逻辑集中在 Controller / Service / Mongoose，而不是散落在 Next Route 里。

**EN:** NestJS is required and runs as the sole API on port 3001. Next.js is UI-only on 3000, so the API is reusable by scripts and Swagger.

---

### Q2：架构图里 Bee 是什么？和 NestJS 是什么关系？

**答：** **Bee** 是 NestJS 里的一个 **后台模块**（Cron + Service），不是单独进程。它按 **65 秒 / 约 3 条** 的频率从 **Jikan** 拉元数据、从 **Bangumi** 做映射，写入 MongoDB 的 **`AnimeMirror`**。用户请求时间表、当季推荐时，读路径 **优先查镜像**，避免每次打开页面都打外部 API。

**EN:** Bee is a NestJS background module that mirrors Jikan/Bangumi into MongoDB on a polite schedule. Reads use the mirror first.

---

### Q3：MongoDB 里主要有哪些集合？各自职责？

**答：**

| 集合 | 职责 |
|------|------|
| **`AnimeEntry`** | 用户私有进度：`status`、`rating`、`completedAt`、`episodesWatched` 等 |
| **`AnimeMeta`** | 公有元数据缓存（Cache-Aside）：`title`、`imageUrl`、`episodes`… 按 `malId` 全局唯一 |
| **`AnimeMirror`** | Bee 写入的 Jikan 全量 JSON + Bangumi 字段（`titles.cn`、`bangumi.weekday` 等） |
| **`BeeState`** | Bee 断点续爬游标（季度回滚等） |

**设计亮点：** **Ownership 双表** — 用户表不含 `title/封面`，避免多用户扩展时把元数据混进进度表。

**EN:** AnimeEntry is user progress; AnimeMeta is shared metadata cache; AnimeMirror is Bee’s mirror with Bangumi enrichments.

---

### Q4：外部 API 失败或限流时，整个系统还能用吗？

**答：** 分场景：**读镜像/缓存** 仍可服务时间表、当季推荐；**创建条目** 有 **柔性模式（Soft Mode）** — 若当时拉不到 `AnimeMeta`，仍允许写入 `AnimeEntry`，响应里 `animeMeta` 可为 `null`，后台 Bee 后续补齐。Jikan **429** 时后端返回 **`UPSTREAM_RATE_LIMIT`**，Bee 进入 **backoff**，可通过 `GET /api/bee/status` 查看。

**EN:** Mirror reads still work; POST /api/anime can succeed with animeMeta null; 429 is handled with backoff and explicit error codes.

---

## 二、API-first 与 Swagger（第 7 页）

### Q5：什么叫 API-first？你们怎么证明「契约优先」？

**答：** 开发顺序是 **先定 OpenAPI 契约（`anitrack-backend/swagger.json`）→ 实现 Nest 端点 → 前端/测试只依赖契约**。证据有三：① Swagger UI **`http://localhost:3001/api-docs`**；② **`anitrack-tester/contract-validator`** 对照运行时做 HTTP 冒烟；③ 前端 **`lib/api.ts`** 只请求 `/api/*`，不在 React 里复制校验/统计规则。

**EN:** We maintain swagger.json first, implement NestJS against it, and verify with contract tests and a thin frontend.

---

### Q6：需要单独写 Word/PDF API 文档吗？

**答：** **不需要。** OpenAPI 即文档；答辩展示 **Swagger UI + Try it out** 即可。课程提交包里的 **`5-Anitrack/openapi.json`** 与仓库 **`swagger.json`** 同源。

**EN:** No separate document — swagger.json and /api-docs are the documentation.

---

### Q7：错误响应长什么样？前端怎么处理？

**答：** 统一信封：

```json
{
  "error": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "Human readable message",
    "details": [{ "path": "status", "reason": "..." }]
  }
}
```

例如非法状态迁移 → **HTTP 409** + `code: INVALID_STATUS_TRANSITION`；校验失败 → **400** + `VALIDATION_ERROR`。

**EN:** All errors use `{ error: { code, message, details } }` — e.g. 409 for invalid status transitions.

---

### Q8：Swagger 里 POST 和 GET 都测吗？为什么有些 Bee 接口是 POST？

**答：** **契约测试按 OpenAPI 声明的方法** 探测（GET/POST 分开）。Bee 的 **`seed-step` / `sync-step` / `bangumi-map` / `map-mal-ids`** 是 **运维/手动触发**，用 POST 避免误 GET 触发同步；冒烟时 POST 若遇 **429** 记为 **警告** 而非失败。

**EN:** Contract tests respect declared HTTP methods; Bee POST endpoints are operational triggers, not casual GETs.

## 三、用户路径（第 8 页）

### Q9：四个页面分别调用哪些核心 API？

**答：**

| 页面 | 主要 API |
|------|----------|
| **Dashboard `/`** | `GET /api/stats/summary`、`GET /api/anime?status=WATCHING`、`GET /api/anime-meta/seasonal-random` |
| **Timetable `/timetable`** | `GET /api/anime-meta/timetable?pastDays=14&futureDays=14` |
| **Library `/library`** | `GET /api/anime-meta/search?q=`、`GET/POST/PATCH/DELETE /api/anime` |
| **Profile `/profile`** | `GET /api/stats/heatmap`、`GET /api/stats/activity?month=YYYY-MM` |

**EN:** Each page maps to a small set of REST endpoints — stats, anime CRUD, anime-meta discovery.

---

### Q10：为什么 Timetable 和 Dashboard 推荐不直接调 Jikan？

**答：** **读路径 Mirror-first：** 当季数据已在 **`AnimeMirror`（tier=seasonal）**；`seasonal-random` 用 MongoDB **`$sample`**，**该接口不发起 Jikan HTTP**。时间表同理，依赖镜像里的 `broadcast` + Bangumi 星期/时刻。只有 **搜索、Cache-Aside 未命中** 等路径才同步请求 Jikan。

**EN:** Timetable and seasonal picks read AnimeMirror only — no Jikan HTTP on those hot paths.

## 四、数据流与缓存（第 9 页）

### Q11：「添加一部番」的完整数据流是什么？

**答：**

1. 前端 **`POST /api/anime { malId, status? }`** — 只传 `malId`（+ 可选私有字段）  
2. 后端 **Cache-Aside**：`getOrFetchByMalId(malId)` → 先查 **`AnimeMeta` / 新鲜 Mirror** → 未命中再请求 Jikan 并 upsert  
3. 写入 **`AnimeEntry(userId, malId, status, …)`** — `(userId, malId)` 唯一  
4. 响应 **嵌套 `animeMeta`**，前端直接渲染，无需再 join  

**EN:** POST malId only → cache-aside AnimeMeta → create AnimeEntry → return nested animeMeta.

---

### Q12：AnimeMeta 和 AnimeMirror 有什么区别？为什么两个都要？

**答：** **`AnimeMeta`** 是面向 API 的 **规范化快照**（轻字段，列表/详情直接用）。**`AnimeMirror`** 存 Jikan **原始 JSON + Bee 维护的 Bangumi 扩展**，供时间表分桶、随机推荐、映射补全。Mirror 命中时可 **落地/刷新 AnimeMeta**（Mirror-first 读路径）。

**EN:** AnimeMeta is the normalized API cache; AnimeMirror is the full mirror with Bangumi fields for schedule and sync.

---

### Q13：除了 MongoDB 影子库，还有别的缓存吗？

**答：** 有。Nest **`CacheModule`** 对 **Jikan HTTP** 做 **24 小时** URL 级缓存，降低 429。与 MongoDB Cache-Aside **互补**：内存缓存加速重复 Jikan URL；Mongo 持久化跨重启。

**EN:** Yes — 24h in-memory cache for Jikan URLs, plus persistent MongoDB cache-aside.

---

### Q14：Bangumi 映射在数据流里处于哪一步？

**答：** **后台增强，不阻塞主 CRUD：** Bee Cron 对当季 mirror 做标题匹配 → 写 `bgmId`、`titles.cn`、`bangumi.weekday`；清单/推荐读路径缺中文时 **`[i18n-map]`** 后台批次映射；客户端启动还可 **`POST /api/anime-meta/mirror-i18n-sync`** 补全 seasonal 池。前端用 **`pickAnimeTitle(locale, …)`** 从 API 多语言字段选显示，**不需额外词典**。

**EN:** Bangumi mapping runs in the background; titles are merged into API responses for i18n display.

---

### Q15：当季推荐切换语言为什么会/不会换一批番？

**答（当前实现）：** API **一次返回** `titleCn/titleEn/titleJp` 等；Dashboard 的 React Query **`queryKey` 不含 `locale`**，切换语言只改 **`pickAnimeTitle`**，**不会重新 `$sample`**。只有点「换一批」才重新随机。

**EN:** Language switch only changes which title field we display — not the random sample set.

---

## 五、后端业务逻辑（第 10 页）

### Q16：状态机有哪些规则？非法迁移会怎样？

**答：** 后端 **`AnimeService`** 维护允许边，例如：`PLANNED → WATCHING|ON_HOLD|DROPPED|COMPLETED`，`WATCHING → ON_HOLD|DROPPED|COMPLETED` 等（详见 `PROJECT_BLUEPRINT.md` §5.1）。非法迁移 → **409** + **`INVALID_STATUS_TRANSITION`**。变为 **`COMPLETED`** 时自动维护 **`completedAt` / `completedDates`（YYYY-MM-DD）**。

**EN:** Allowed transitions are enforced in NestJS; illegal ones return 409 INVALID_STATUS_TRANSITION.

---

### Q17：热力图强度 0–4 怎么算？为什么不在前端算？

**答：** **`GET /api/stats/heatmap`** 在 MongoDB **Aggregation Pipeline** 按月聚合 `addedCount`（`createdAt`）、`completedCount` / `episodeCount`（`completedAt`）。强度权重 **`score = addedCount + completedCount`**，映射：**0→0，1→1，2–4→2，5–8→3，≥9→4**（`monthly-heatmap-intensity.ts` + Jest 单测）。前端只渲染 `intensity` 颜色，符合「**业务逻辑在后端**」。

**EN:** Intensity is computed in MongoDB aggregation on the server; the frontend only renders the 0–4 value.

---

### Q18：为什么 Activity 明细也单独有 API？

**答：** 若前端拉全量 `AnimeEntry` 再按月份 filter，既慢又不一致。因此 **`GET /api/stats/activity?month=YYYY-MM`** 在后端聚合该月 Added/Completed 列表；Profile 点击格子只请求一个月。

**EN:** Monthly activity is a dedicated API so we don’t paginate the entire library on the client.

---

### Q19：Bee 的「65 秒 / 3 条」是怎么定的？有什么优先级？

**答：** 礼貌爬取，降低 Jikan **429** 风险。优先级：**seasonal > top_1y (40) > top_5y (100) > top_all (200) > backfill**；各 tier 有不同 **TTL**（如 seasonal 7 天）。启动 seed 遇 429 会 **backoff**，可 **`POST /api/bee/seed-step`** 手动续跑。

**EN:** Polite rate — 3 items every 65s with tier priorities and TTL-based freshness.

---

### Q20：目前用户身份怎么区分？多用户怎么办？

**答：** 现阶段 **单用户**：`@CurrentUser()` 装饰器 dev fallback 为 **`TEMP_USER_ID`**；所有查询/聚合 `$match userId`。未来加 Auth 时只需替换 CurrentUser 来源，**`(userId, malId)` 复合唯一索引** 已预留（Blueprint §3.10）。

**EN:** Single-user TEMP_USER_ID for now; schema is ready for real userId when we add auth.

## 七、演讲稿补充（讲者 B 稿可能遗漏 · 建议口头补一句）

> 对照 `anitack-B演讲稿.docx`（第 6–10 页）与当前实现；下列为稿中未展开、答辩时容易被追问的点。

### Q23：前端和后端分别跑在哪个端口？为什么分开？

**答：** **Next.js 前端 `http://localhost:3000`** 只负责页面与交互；**NestJS API `http://localhost:3001/api`** 是唯一业务数据入口，Swagger 在 **`/api-docs`**。分开是为了满足课程 **NestJS 后端** 要求，并让 API 可被 **脚本客户端 / 契约测试** 独立调用，而不是绑死在 Next Route Handlers 上。

**EN:** UI on 3000, NestJS API on 3001 — separate so the API is framework-independent and testable.

---

### Q24：为什么要把 AnimeMeta 和 AnimeEntry 拆成两张表？

**答：** **Ownership 拆分**：`AnimeMeta` 存 **公有、可缓存** 的番剧元数据（按 `malId` 全局唯一）；`AnimeEntry` 只存 **用户私有** 进度（`status`、`rating`、`completedAt`…），通过 `(userId, malId)` 关联。用户表 **不含 title/封面**，避免多用户时把 Jikan 元数据复制进每条进度记录，也便于 Cache-Aside 与 Bee 镜像 **一处更新、多处复用**。

**EN:** AnimeMeta is shared metadata cache; AnimeEntry is per-user progress — clean separation for multi-user and cache-aside.

---

### Q25：除了「409」，错误响应具体长什么样？

**答：** 全 API 统一信封：

```json
{
  "error": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "...",
    "details": [{ "path": "status", "reason": "..." }]
  }
}
```

非法状态迁移 → **HTTP 409** + **`code: INVALID_STATUS_TRANSITION`**；校验失败 → **400** + **`VALIDATION_ERROR`**；Jikan 限流 → **429** + **`UPSTREAM_RATE_LIMIT`**。前端与契约测试都依赖同一结构。

**EN:** Uniform `{ error: { code, message, details } }` — e.g. 409 INVALID_STATUS_TRANSITION for bad status changes.

---

### Q26：MongoDB 之外还有缓存吗？怎么防 Jikan 429？

**答：** 有两层：**① MongoDB Cache-Aside**（`AnimeMeta` + `AnimeMirror` 持久化）；**② Nest `CacheModule`** 对 Jikan HTTP 请求做 **24 小时** URL 级内存缓存。再加上 **Bee 65s/3 条** 礼貌爬取、429 **backoff**、读路径 **Mirror-first**，从「少请求、缓请求、本地读」三方面降压。

**EN:** MongoDB cache-aside plus 24h in-memory Jikan cache, polite Bee sync, and mirror-first reads.

---

### Q27：Timetable 页面到底是「日期条」还是别的布局？

**答（与当前实现一致）：** 不是「顶部选一天 + 下方单列列表」的旧描述，而是 **±2 周（`pastDays=14&futureDays=14`）多列横向滚动**：每列宽约 **200px** 代表一个柏林日历日，**今天列高亮**，左右箭头导航；列内全量渲染 API 返回条目。星期标签由前端 **`formatWeekdayBerlin(date, locale)`** 按 UI 语言显示。

**EN:** Multi-column horizontal scroll for ±2 weeks — not a single-day list under a date strip.

---

### Q28：Dashboard「当季推荐」的数据从哪来？会打 Jikan 吗？

**答：** **`GET /api/anime-meta/seasonal-random`** 只对 MongoDB **`AnimeMirror`（tier=seasonal）** 做 **`$sample`**，**该读路径不发起 Jikan HTTP**。抽样优先已有 **`titles.cn`** 的条目；缺中文时对本次抽中的 `malId` **同步 Bangumi 映射**后再返回。客户端启动还可 **`POST /api/anime-meta/mirror-i18n-sync`** 后台补全 seasonal 池（`MirrorI18nBootstrap`）。

**EN:** Seasonal picks are MongoDB $sample from AnimeMirror only — no Jikan on that path, with Bangumi i18n enrichment.

---

### Q29：有 swagger.json 就够了吗？怎么保证实现没跑偏？

**答：** 不够只「有文件」——我们还跑 **`anitrack-tester/contract-validator`**：读取 **`swagger.json`**，对声明的路径/方法做 HTTP 冒烟，校验状态码与响应结构（AJV + SwaggerParser）。`CONTRACT_PENDING_PATHS` 为空时为严格模式。这才是 **API-first 可验证** 的闭环，比另写 Word 文档更有说服力。

**EN:** contract-validator smoke-tests the live API against swagger.json — executable contract, not just a static file.

---

### Q30：热力图强度 0–4 的具体规则？为什么还有 summary / activity 接口？

**答：** **`GET /api/stats/heatmap`** 在服务端按月聚合；权重 **`score = addedCount + completedCount`**（`episodeCount` 仅展示不参与强度），映射：**0→0，1→1，2–4→2，5–8→3，≥9→4**（`monthly-heatmap-intensity.ts`，**Jest 单测**）。另设 **`GET /api/stats/summary`**（Dashboard/Profile 顶栏指标）和 **`GET /api/stats/activity?month=`**（点击某月明细），避免前端 **分页拉全库再 filter**，保证性能与口径一致。

**EN:** Intensity thresholds are server-side with Jest unit tests; summary and activity are separate aggregates to avoid client-side full-library filtering.

---

### Q31：添加番剧时，如果 Jikan 暂时拉不到元数据怎么办？

**答：** **柔性模式（Soft Mode）**：`POST /api/anime` 在抓取/读取 `AnimeMeta` 失败时 **仍允许创建 `AnimeEntry`**，响应中 **`animeMeta` 可为 `null`**，并记录日志；Bee 与后续读路径会 **被动补齐** 镜像/元数据。演示时可说明：核心进度数据不依赖第三方即时可用。

**EN:** Soft mode — entry creation succeeds even if meta fetch fails; animeMeta may be null until Bee backfills.

---

### Q32：整站中英文切换时，番剧标题和「换一批推荐」会怎样？

**答：** **两层解耦**：壳层按钮/导航走 **`I18nProvider` 词典**；番剧标题走 API 返回的 **`titleCn/titleEn/...`** + 前端 **`pickAnimeTitle(locale, …)`**，**不改** API 枚举值（如 `WATCHING`）。当季推荐的 React Query **`queryKey` 不含 `locale`** — **切换语言只换显示字段，不会重新随机抽 4 部**；只有点「换一批」才重新 `$sample`。

**EN:** Locale switch changes display fields only — seasonal picks stay the same malIds until the user shuffles.

---

### Q33：PPT 第 11 页写热力图单测在 Vitest，实际在哪？

**答（串问备用）：** 第 6–10 页主讲后端逻辑，若被问到测试细节：**月度强度映射单测在后端 Jest**（`monthly-heatmap-intensity.spec.ts`），不在 Vitest。前端 Vitest 主要是 **heatmap 集成/代理** 等。答辩以 **「强度规则在 Nest + Jest 覆盖」** 为准即可。

**EN:** Heatmap intensity unit tests are Jest on the backend, not Vitest — Vitest covers integration paths.
